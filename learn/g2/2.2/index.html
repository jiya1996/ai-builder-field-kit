2.2架构透视与信任边界

本节任务：亲手画结构图和信任边界图。

输入什么已经评审的一页产品规格，以及核心流程中会经过的数据和外部服务。
输出什么两张架构图，能指出密钥与权限必须放在哪里。
学会什么看懂页面、服务端、数据库、模型和密钥的数据流。
本节阅读方法

  2. 照着步骤动手做
  3. 逐条完成验收
  4. 遇到问题看常见坑
不要只看

代码块、提示词和检查框都是本节任务的一部分。

白话讲清

这一节回答"系统由什么组成、数据怎么流、为什么这样组合"。你要亲手画两张图（手画拍照即可，不要求工具）：

图一：结构图。 把 2.0 的地图抄一遍，但每个方框里写上你自己项目的具体内容（页面叫什么、表叫什么、接口叫什么）。

图二：信任边界图。 用一条红线把系统切成两半：

        【不可信区：用户的浏览器】
  页面代码、用户输入 ← 这里的一切都可能被查看、被伪造
──────────────红线（信任边界）──────────────
        【可信区：你的服务端 + Supabase】
  密钥、身份校验、权限判断、数据库规则 ← 只能放在这里

三条推论，本关后面全部会用到：

  1. 前端"隐藏按钮"不是安全措施——按钮藏得住，接口藏不住。
  2. 一切校验（是不是本人、能不能看这条数据）必须发生在红线以下。
  3. 密钥出现在红线以上的任何位置 = 泄露。

默认技术栈与取舍（照抄，不纠结）

第一版默认栈：Next.js + TypeScript + Supabase + Vercel。理由只有三条：一体化（前端后端一个项目）、免运维（不用买服务器）、生态大（AI 搭档最熟悉，报错资料最多）。其他栈不是不好，是同时学两条路线必死。等你通了关卡3，换栈是一周的事。

验收

  • 能指着图回答：用户点"保存灵感"后，数据经过哪几站？密钥住在哪一站？
