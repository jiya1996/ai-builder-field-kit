1.2Codex 协作小循环 + Git 后悔药

本节任务：完成一个真实页面任务，并亲手回滚一次乱码提交。

输入什么可运行的项目、首个 Git 快照和一张足够小且可验收的页面任务卡。
输出什么一条完整协作记录 + 一次成功回滚。
学会什么掌握计划—确认—实现—Diff—验证—提交的小步循环。
本节阅读方法
  1. 先读白话讲解
  2. 照着步骤动手做
  3. 逐条完成验收
  4. 遇到问题看常见坑
不要只看

代码块、提示词和检查框都是本节任务的一部分。

白话讲清

和 Coding Agent 合作的正确节奏不是"一句话生成整个项目"，而是小循环：

阅读现状 → 明确目标 → 它提出计划 → 你确认 → 小步实现
→ 看 Diff（它改了哪些文件哪些行）→ 运行验证 → 人工验收 → git 提交记录状态

一次循环只做一个可验证的任务。为什么？大任务出错时你不知道错在哪一步；小任务出错，回滚成本是几分钟。

Git 在循环里的位置：每次让 AI 动手前，确保上一个稳定状态已提交。 这样任何一步搞砸，一条命令回到安全点。

跟我做（用一个真实小任务练习整个循环）

任务卡示例（发给搭档）：

【任务】给首页做一个标题区
【验收条件】
1. 页面顶部显示产品名"纪要→清单"和一句副标题
2. 手机宽度下不换行错乱
【范围】只允许修改首页文件和全局样式；不要引入任何新依赖
【流程】先告诉我你的修改计划（涉及哪些文件），我确认后再动手；
完成后展示 Diff 摘要，等我在浏览器确认，再提交 git。

跑完整个循环后，做一次回滚演习：

请故意把首页标题改成乱码并提交，然后教我用 git 命令查看提交历史，
并把项目回退到上一个提交。我要亲手输入回退命令。

验收

  • 完整走过一次"计划→确认→实现→Diff→验证→提交"循环
  • 亲手执行过一次回滚，页面恢复正常
  • 能说出：为什么让 AI 动手前要先提交？
本节完成标准

不是“读完了”，而是证据已经产生。

一条完整协作记录 + 一次成功回滚。
