01

模型能力不是产品能力

模型只根据输入生成概率性结果。产品仍需负责输入限制、上下文选择、输出校验、失败状态、权限、成本和用户能否采取下一步行动。

02

结构化输出是模型与软件的合同

自然语言适合人读，JSON 适合程序继续处理。Schema 规定字段和类型，服务端验证后才能让结果进入数据库或触发下一步。

03

RAG 不是让模型拥有知识库

系统先检索相关资料，再把选中的内容放进上下文。检索质量、引用和资料新鲜度决定答案能否被追溯。

1.4一次模型调用的解剖第 3 天展开正文
输入

已经跑通的产品壳、一组真实输入和你希望 AI 稳定返回的结果格式。

动手做

画出请求—响应图，写好 system 指令初稿。

完成证据

能回答计费、密钥与 JSON 校验三个核心问题。

为什么要解剖

接下来你要花真金白银调用模型。花钱之前，必须看穿这笔钱买的是什么、藏在哪些环节。这一节没有代码任务，但决定你以后所有 AI 功能的质量和成本。

一次调用的完整解剖图

你的服务端代码
   │  组装一次请求（花钱从这里开始计量）
   ▼
┌─ 请求包 ────────────────────────────────┐
│ ① 模型名：决定能力/速度/单价               │
│ ② 消息列表：                             │
│    system 指令  ← 你产品的"岗位说明书"      │
│    user 内容    ← 用户这次贴进来的纪要      │
│   （多轮对话时还有历史消息，本关用不到）       │
│ ③ 参数：温度(稳定↔发散)、最大输出长度        │
│ ④ 密钥：证明"扣我的账"——所以绝不能泄露      │
└──────────────┬─────────────────────────┘
               ▼  模型服务商
┌─ 响应包 ────────────────────────────────┐
│ 模型输出的文字（或结构化 JSON）             │
│ 用量：输入 token 数 + 输出 token 数 → 费用   │
└──────────────┬─────────────────────────┘
               ▼
你的服务端解析输出 → 返回给页面展示

五个必须刻进脑子的结论

  1. Token 是计费单位，输入和输出都算钱。粘贴 1 万字纪要 ≈ 上万输入 token。所以"限制输入长度"不是抠门，是产品设计。
  2. system 指令是你产品的灵魂。同一个模型，A/B/C 三个工具的差别几乎全在 system 指令里。
  3. 温度不是"聪明度"。提取任务这种要稳定的场景用低温度；文案打磨这种要花样的场景可以调高。
  4. 模型输出天生不稳定。要让程序消费结果（比如渲染成清单），必须要求结构化输出（JSON）并在代码里校验，不能指望它"每次都乖"。
  5. 密钥 = 你的钱包。出现在浏览器代码、GitHub 仓库、截图里的任何一处，都等于把钱包丢在路上。这就是为什么调用必须发生在服务端。

验收（口头即可，但要真答）

  • 一次调用的钱由哪两部分组成？
  • 为什么密钥不能放在前端页面里？（提示：浏览器里的代码任何人都能查看）
  • 你的工具 system 指令初稿写好了吗？（写在任务卡里，下一节直接用）
1.5接上真正的 AI第 4–5 天展开正文
输入

可用的模型 API、服务端环境变量、system 指令和约定好的 JSON 结构。

动手做

接入真实 API，限制输入，校验 JSON，保留错误重试。

完成证据

3 组输入成功、错误密钥可恢复、单次成本已记录。

跟我做

第一步：拿到密钥并安全存放。 在你选的模型服务商（国内推荐 DeepSeek / 智谱 / Kimi 任一）注册、充值 10–50 元、创建 API Key。然后：

我拿到了模型服务商的 API Key。请：
1. 在项目根目录创建 .env.local，教我把密钥放进去（我自己粘贴，不发给你）
2. 确认 .gitignore 已排除 .env.local
3. 告诉我怎么验证"密钥没有被提交进 git 历史"

第二步：创建服务端接口 + 真实调用。 任务卡：

【任务】把"提取行动清单"接上真实模型
【实现要求】
1. 创建服务端接口 /api/extract：接收纪要文本，调用【服务商】的模型 API
2. 密钥只从环境变量读取，前端代码里不出现任何密钥
3. system 指令使用我提供的这段：【贴入你 1.4 写的指令初稿，要求：
   角色=会议行动项提取助手；只依据原文提取，不编造；
   输出严格为 JSON 数组，每项含 task/owner/due 三个字段，缺失字段填 null】
4. 要求模型输出 JSON；服务端解析并校验结构，校验失败返回明确错误
5. 前端把假数据替换为真实接口结果；加载/错误状态沿用 1.3 的壳
6. 限制输入最长 8000 字，超出时前端直接提示，不发请求
【验收条件】
1. 贴入真实纪要能返回正确清单；2. 断网/密钥错误时页面显示友好错误并可重试；
3. 浏览器开发者工具的网络面板里看不到密钥
【流程】同铁规矩

第三步（推荐加分项）：流式输出。 如果你选了 B（文案打磨），追加一张任务卡让结果逐字出现——体验差异巨大，也顺便理解"流式"这个词。A/C 结构化输出不需要流式。

第四步：算一笔账。 让搭档在响应里打印本次调用的 token 用量，你用服务商单价手算一次成本，记进通关登记。

验收

  • 真实纪要 → 正确清单，连续 3 次不同输入都成功
  • 故意填错密钥 → 页面出现友好错误而不是崩溃 → 改回后恢复
  • 网络面板检查过：请求发往你自己的 /api/extract，密钥不可见
  • 知道自己单次调用大约花多少钱

常见坑

  • 模型偶尔输出 JSON 外的废话导致解析失败：在 system 指令里加"只输出 JSON，不要任何解释文字"，并保留代码校验兜底。这不是 bug，是第 1.4 节结论 4 的现场版。
  • 429 报错：请求太频繁或余额不足，急救室 ER-2 有对应急救卡。
2.8AI 自动标签与摘要第 11–13 天展开正文
输入

稳定保存的用户内容、可用模型 API、登录状态和费用上限假设。

动手做

异步生成标签摘要，加入登录校验、频率限制与输入截断。

完成证据

AI 失败不丢数据、未登录被拒、COST.md 有真实推演。

白话讲清

这里复用关卡1 的全部功力（服务端调用、结构化输出、校验兜底），新增两个真产品才有的问题：

  1. 成本会随用户增长：自用工具花的是你的小钱；多用户产品花的可能是大钱。
  2. 防盗刷：接口公开在互联网上，必须限制"谁、多频繁、花多少"。

跟我做

【任务】保存灵感时自动生成标签和摘要
【实现】
1. 服务端接口 /api/enrich：输入灵感文字，调用模型返回 JSON
   {tags: 最多3个中文标签, summary: 不超过30字的一句话摘要}；
   system 指令要求只依据输入内容、禁止编造、只输出 JSON
2. 新建流程：先保存灵感（保证不丢），再异步调用 enrich 回填 tags/summary；
   AI 失败不影响保存，卡片显示"标签生成失败·重试"
3. 防护三件套：a) 单用户每分钟最多 5 次 enrich（超出返回明确提示）；
   b) 输入截断到 2000 字再送模型；c) 未登录调用 /api/enrich 直接拒绝
4. 在服务端日志打印每次调用的 token 用量
【验收】存一条灵感几秒后标签浮现；AI 挂了灵感也不丢；
       连续快速保存第 6 条时出现频率限制提示；退出登录后用工具直调接口被拒

再做一次成本推演（写进 docs/COST.md）：单次 enrich 成本 × 预估每用户每天条数 × 用户数 = 日成本。用你的真实 token 数据算。"看得见成本"是 AI Builder 和"接了个 API 的人"的区别。

验收

  • 验收四连全部通过
  • COST.md 有你自己的成本推演数字
学完必须掌握
  • 能画出一次模型请求与响应
  • 能设计并验证结构化输出
  • 能判断何时直接提示、何时需要检索
