S00

第一次成功

一个网页怎样从你电脑里的文件，变成别人能访问的网址？

理论学习
2–3 小时
实战周期
半天
输入什么

一台电脑、可联网环境、你的姓名与一句自我介绍。

输出什么

公开网页、GitHub 仓库，以及一次故障—定位—修复记录。

学会什么

解释本地文件、浏览器、Git、GitHub、服务器和 URL 的完整链路。

KNOWLEDGE

不是记名词，而是理解系统因果。

本阶段只学习马上会在项目中使用和验证的知识。

文件与文件夹HTML / CSS / JavaScript浏览器终端GitGitHubURLHTTP部署404 / Console
01

网页不是一张图片

HTML 描述页面有什么，CSS 决定它长什么样，JavaScript 决定点击后发生什么。浏览器读取这些文件并把它们解释成你看到和操作的页面。

02

Git、GitHub 和部署不是一回事

Git 在本地记录版本；GitHub 保存并协作管理仓库；部署平台把某个版本放到公开服务器。少掉任何一层，结果和恢复方式都不同。

03

URL 是地址，HTTP 是取东西的规则

浏览器根据 URL 找到服务器，再通过 HTTP 请求资源。404 通常表示路径不存在；Console 报错通常表示页面代码运行时出错。

0.1装上 AI 编程搭档40 分钟展开正文
输入

可联网的电脑、一个可注册工具的邮箱，以及一个准备专门放项目的空文件夹。

动手做

创建 my-first-site，并让 Agent 确认当前工作目录。

完成证据

工具可用、目录正确、能看见文件改动。

白话讲清

AI 编程搭档（Coding Agent）和普通聊天 AI 的区别只有一个：它能直接操作你电脑上的一个文件夹——创建文件、修改文件、运行命令，每一步高风险动作都会先征求你的同意。

你要建立的第一个概念：它在哪个文件夹里工作，就只动那个文件夹。 这个文件夹叫"项目"。

本资料包主线使用 Codex（终端型，也有图形界面版）。如果你更习惯图形界面，Cursor、Claude Code 均可，主线所有提示词通用；后文对差异步骤会单独标注。

跟我做

  1. 注册并登录你选择的工具（见《开始之前 S-2》账号清单）。
  2. 在桌面新建一个文件夹，命名为 my-first-site（英文、无空格——这是唯一的命名要求，原因见词典"路径"词条）。
  3. 用你的工具打开这个文件夹：
    • 图形界面类（Cursor 等）：File → Open Folder，选中 my-first-site。
    • 终端类（Codex / Claude Code）：打开终端，输入 cd （注意 cd 后有空格），把文件夹拖进终端窗口回车，再输入启动命令（如 codex 或 claude）。
  4. 发第一条消息测试：
你好，请告诉我你现在的工作目录是哪个文件夹，以及你能为我做什么。

验收（全部打勾才算过）

  • 工具已登录，能正常回复消息
  • 它回答的工作目录就是你刚建的 my-first-site
  • 你知道去哪里看它创建/修改了哪些文件

常见坑

  • 安装报错：把完整报错文字原样发给工具本身，让它教你解决——这就是你们合作的第一课。
  • 回复超时：先查网络；终端工具确认没开在错误的目录。
  • 它请求"允许运行命令"：先读一眼它要干什么，看得懂就允许。看不懂？复制那条命令问它"这条命令是做什么的，有风险吗"。
0.2描述 → 生成 → 预览 → 调整40 分钟展开正文
输入

已正确打开的 my-first-site 文件夹，以及你的姓名、身份介绍和联系方式。

动手做

用中文生成 index.html，并完成一次明确的视觉调整。

完成证据

页面能打开，内容是自己的，修改前后可对比。

白话讲清

你将反复使用的核心循环，四拍：描述 → 生成 → 预览 → 调整。

还需要知道两个名词（词典有详细版）：

  • HTML：网页的骨架文件。浏览器读它，渲染成你看到的页面。
  • index.html：网站的默认首页文件名。部署平台会优先找它。

跟我做

  1. 把这段话原样发给你的搭档：
在当前目录创建一个 index.html，做一个个人主页：
- 深色背景，内容居中
- 大标题写我的名字【替换成你的名字】
- 副标题写"我的第一个网页 · 用 AI 做的"
- 下面放三行：我是谁（一句话）、我在学什么、联系方式
- 字体现代好看，有一个克制的淡入动画
不要用任何外部图片链接。
  1. 生成后，在文件夹里找到 index.html，双击用浏览器打开。
  2. 至少做一次具体的修改反馈，例如：
把副标题的颜色调暗一点，三行介绍之间的间距加大，标题入场动画放慢到 1 秒。

注意对比：说"不好看，改一下"是无效反馈；说"标题太大、间距太挤、颜色太亮"才是有效反馈。给 AI 提需求的能力，本质是把主观感受翻译成可验证的描述。 这条原则会贯穿全部五关。

验收

  • 文件夹里存在 index.html
  • 浏览器能正常显示，内容是你自己的信息
  • 完成了至少一次"具体描述"的修改，并刷新看到效果

常见坑

  • 页面空白：让它"检查 index.html 的内容并修复"。
  • 改了没变化：确认文件已保存，浏览器按 Ctrl/Cmd + R 刷新。
  • 它创建到了别的文件夹：回到 0.1，确认工作目录。
0.3让全世界能打开它40 分钟展开正文
输入

本地可正常打开的 index.html，以及可用的 GitHub 和部署平台账号。

动手做

把网页推到 GitHub 并发布到公开托管地址。

完成证据

手机流量可打开，至少一位朋友访问成功。

白话讲清

部署就是把你电脑里的文件放到一台公开的服务器上，让任何人通过网址访问。你的电脑关机后网页也一直在线。

静态网页（只有 HTML/CSS/JS）可以免费托管。我们用 Vercel（若访问不稳定，改用 Cloudflare Pages 的"直接上传"方式，步骤等价）。

这一步会顺手引入两个以后天天用的东西：

  • Git：给你的代码拍快照的工具，改错了能退回去（"编程后悔药"）。
  • GitHub：把快照存在云端的仓库网站，同时也是部署平台的取货口。

现在不需要理解 Git 的原理，跟着做，关卡1 会正式训练它。

跟我做

  1. 发给搭档：
帮我把当前项目发布到互联网上，用 GitHub + Vercel 的方式：
1. 在当前目录初始化 git 仓库，创建合理的 .gitignore，完成第一次提交
2. 一步步指导我在 GitHub 网页上创建一个新仓库（我是零基础，每一步都告诉我点哪里）
3. 指导我把本地代码推送上去
4. 指导我在 Vercel 上用 GitHub 登录并导入这个仓库完成部署
每完成一步先停下来等我确认，再进行下一步。
  1. 跟着走完。中途任何报错，原样贴回去。
  2. 部署成功后，Vercel 会给你一个 https://xxx.vercel.app 的网址。
  3. 用手机流量（不连 WiFi）打开这个网址——确认它真的在互联网上。
  4. 把链接发给一个朋友。

验收

  • GitHub 上能看到你的仓库和 index.html
  • 拿到一个 https 开头的公开网址
  • 手机流量下能打开
  • 至少一个人（除你以外）打开过它

常见坑

  • 推送要求登录/密钥：按提示走 GitHub 的浏览器授权即可，让搭档陪你逐步做。
  • 部署后 404：最常见原因是 index.html 不在仓库根目录。发"我的部署打开是 404，请检查 index.html 是否在仓库根目录并修复"。
0.4软件世界最小地图20 分钟展开正文
输入

刚才完成的本地网页、GitHub 仓库和公开链接这三样真实成果。

动手做

沿着一次发布画出文件从本地到线上的路线。

完成证据

能用五句话解释刚才发生了什么。

刚才发生了什么？一张图讲清，这也是你以后所有项目的地图：

┌─ 你的电脑（本地） ──────────────────────────┐
│  项目文件夹 my-first-site/                    │
│    └─ index.html   ← AI 搭档在这里读写文件     │
│  浏览器：读取本地文件，渲染成页面（本地预览）      │
│  终端：对电脑下命令的窗口（git、启动服务都在这里） │
└──────────────┬───────────────────────────┘
               │ git push（把快照推上去）
┌─ GitHub（云端仓库） ─────────────────────────┐
│  存着你代码的每一次快照，可以随时退回任何版本      │
└──────────────┬───────────────────────────┘
               │ Vercel 自动取货、构建、发布
┌─ Vercel（公开服务器） ───────────────────────┐
│  https://xxx.vercel.app  ← 全世界的浏览器都能访问 │
└──────────────────────────────────────────┘

现在只需要记住五句话：

  1. 本地是草稿，线上是出版。 本地改坏了没关系，线上才是给人看的。
  2. 文件夹就是项目，AI 只在项目里干活。
  3. 终端是对电脑说话的窗口，报错也从这里读。
  4. Git 是后悔药：先拍快照，再让 AI 大改。
  5. 推送触发发布：以后每次 git push，Vercel 会自动更新线上版本。

（前端/后端/数据库/API 是什么？关卡2 需要时才讲。现在不需要。这就是"一条不用选择的路径"的含义：只在用到的那一刻学。）

0.5Boss 战：弄坏再修好40 分钟展开正文
输入

一个已上线且能恢复的网页、最近一次正常 Git 快照，以及浏览器开发者工具。

动手做

完成语法破坏、文件名 404、Console 报错三个任务。

完成证据

坏页面、报错文字、修复结果三组截图。

为什么要故意搞破坏

因为你迟早会遇到报错。与其上线前夜第一次遇到，不如现在——在一个改坏了也无所谓的页面上——把"遇到报错该干什么"变成肌肉记忆。

排错三步（急救室的完整五步版的迷你版）：

  1. 看：完整读一遍报错/异常现象，不跳过。
  2. 说：用"我做了什么 / 预期什么 / 实际什么 + 完整报错"描述问题。
  3. 修：把上面的描述交给 AI，验证修复，再想想"为什么"。

跟我做（三个破坏任务，全部完成）

任务一：语法破坏。 用编辑器手动打开 index.html，随便删掉某一行结尾的 > 符号，保存，刷新浏览器。观察页面变化（可能错乱、可能局部消失）。然后发给搭档：

我手动改坏了 index.html，页面显示异常：【描述你看到的现象】。
请找出问题、解释原因，然后修复。修复后告诉我你改了哪里。

任务二：文件名破坏。 把 index.html 改名为 index2.html，重新部署（或让搭档提交并推送）。打开线上网址——404 了。自己先猜一句为什么，再让搭档解释并恢复。

任务三：读一次日志。 发给搭档：

请打开浏览器开发者工具的 Console 面板的方法教给我（我用的是【Chrome/Edge/Safari】），
然后故意在页面里加一行会在 Console 报错的代码，让我亲眼看到红色报错长什么样，
我截图后你再把它修掉。

Boss 战验收（必须留证据）

  • 三个任务全部完成
  • 保存了 3 张证据截图：坏掉的页面 / 报错文字 / 修复后的页面
  • 能用自己的话回答：404 那次的原因是什么？（参考答案在本关末尾）

这三张截图不是形式。从这关起，"做完了"的标准永远是证据，不是感觉，也不是 AI 的一句"已完成"。
